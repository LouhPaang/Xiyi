## 第二章 核心概念：栈域与图域——希夷的"双层所有权"

> 这是希夷区别于 Rust、区别于所有现有语言的**第一性设计**。任何开发者在接触语法之前，需要理解这一点。

### 2.1 为什么需要两个域？

现有语言的困境：
- **Rust**：所有权系统管理通用内存（栈、堆、寄存器），但面对深度学习计算图时束手无策。张量在 GPU/NPU 上的生命周期由框架（PyTorch/TensorFlow）管理，与 Rust 的所有权系统割裂。
- **Python**：无所有权概念，张量内存管理完全依赖引用计数、垃圾回收，无法提供过多的保证。

希夷**在不改造现有所有权系统的前提下，新增一个独立的图域所有权空间，以此计算图**。

### 2.2 栈域（Stack Domain）—— 你熟悉的 Rust 世界

| 属性 | 说明 |
|------|------|
| 管理实体 | 编译器插入的 drop + 词法作用域 |
| 内存位置 | 栈、堆、寄存器 |
| 生命周期 | 词法作用域结束 |
| 值类别 | 任意类型（标量、复合类型、张量） |
| 释放时机 | 所有者离开作用域时 |

栈域就是 Rust 的所有权系统，希夷并没有删减任何核心规则：
1. 每个值有且只有一个所有者
2. 所有者离开作用域时释放
3. 所有权可转移（Move）或借用（Borrow）
4. 默认可变借用（`&mut`）与不可变借用（`&`）互斥

**自举期目标**：完整实现栈域所有权系统。这是编译器的根基，没有商量余地。

### 2.3 图域（Graph Domain）—— 希夷独有的计算图所有权空间

| 属性 | 说明 |
|------|------|
| 管理实体 | 计算图调度器（Graph Scheduler） |
| 内存位置 | NPU HBM / 连续设备内存 / 张量池 |
| 生命周期 | 计算图执行完毕或显式 `.backward()` |
| 值类别 | 仅 `Tensor<T, Shape>` 及其计算图节点 |
| 释放时机 | 图调度器决定，与词法作用域无关 |

图域不是另一个堆，而是一个**语义上独立的内存空间**：
- 它的分配、释放不由 `drop` 控制
- 它的值（张量）在图域内部以节点形式存在
- 它的生命周期与"计算图是否还在执行"绑定

### 2.4 域转移边界：`model` 块是单向阀门

```xiyi
// 栈域：weight 由编译器管理
let weight: Tensor<f32, [784, 256]> = load_weights();

// model 块：所有权转移给图调度器
let handle = model MLP {
    fn forward(&self, x: Tensor<...>) -> Tensor<...> {
        x.linear(weight, 256)
    }
};

// 栈域：weight 已变为 uninitialized
// let w2 = weight;  // ❌ 编译错误：use of moved value
```

**转移语义**：
- **非 `persist` 张量**：Move 语义，栈域变量置为 `uninitialized`
- **`persist` 张量**：共享不可变借用语义，栈域可读不可写，直到 `DiffHandle` 被消费

### 2.5 域穿透性：`persist` 修饰符

```xiyi
persist var weight: Tensor<f32, [256, 784]> = init();
let handle: DiffHandle<Tensor<...>> = model MLP {
    fn forward(&self, x: Tensor<...>) -> Tensor<...> {
        x.linear(weight, 256).relu()  // weight 作为图域持久化参数
    }
};
// ❌ 编译错误：weight 被 handle 不可变借用
// weight = new_weight;
let grads = handle.backward();  // handle 被消费，借用释放
weight = new_weight;  // ✅ 现在合法
```

**冻结边界**：`persist var` 的冻结绑定到 `DiffHandle` 的生命周期，而非模糊的"图域执行期"。这是编译器可以静态检查的。

### 2.6 `DiffHandle<T>`：图域向栈域回传信息的唯一合法通道

`DiffHandle<T>` 同时持有：
1. **栈域结果**：最后一次正向传播的输出张量（已拷贝回主机内存）
2. **图域句柄**：指向计算图内部状态的不可复制指针

```xiyi
let out: DiffHandle<Tensor<f32, [B, 10]>> = model.forward(input);
print_tensor(out.value());      // 栈域侧：直接读取结果值
let grads: GradMap = out.backward();  // 图域侧：触发反向传播，消费句柄
```

**关键约束**：
- 实现 `ExecutorLocal`，显式禁止 `Send` 与 `Sync`（不可跨 Actor/线程传递）
- 必须先调用 `.backward()`、`.execute()` 或 `.discard()` 物化或释放图域资源后，相关的 `persist` 借用才解除
- 携带 `#[must_consume]` 属性：strict 模式下未显式消费即离开作用域 → 编译错误

### 2.7 自举期的图域策略

自举期编译器**无 NPU 后端**，图域代码采用**语义保留的桩策略**：

| 图域特性 | 自举期行为 | 静态检查 |
|---------|-----------|---------|
| `model` 块 | 降维为 `struct + implement`，`forward` 体置空 | ✅ 类型签名、形状约束、隐私标签全检查 |
| `DiffHandle` | 定义为不透明类型，方法体 panic | ✅ `#[must_consume]` 强制 |
| `persist` | 按普通 `let` 处理，借用检查正常 | ✅ 冻结边界检查 |
| `tensor.*` 算子 | 解析为内建函数调用，不生成代码 | ✅ 形状推断、效果标注 |
| `backward()` | 桩函数，返回空 `GradMap` | ✅ 敏感度类型推导 |

这意味着，自举期可以编写、编译、类型检查所有图域代码，但无法实际运行训练或推理。
图域的"自举期实现"不是不实现，而是"实现全部静态语义，运行动态占位"。这要求编译器前端必须完整支持图域的类型系统、形状推断、所有权规则，只有代码生成阶段输出桩代码。

## 第三章 自举期目标：永不进入 Gate 的最小子集

### 3.1 "永不进入 Gate"的精确含义

《最小子集概要》v0.1.9.6_Delta 定义了自举编译器必须支持的全部特性。"永不进入 Gate"意味着，这些特性不依赖任何外部系统（如 WujiOS AI 子系统、NPU 驱动），仅靠编译器自身和 CPU 即可完整执行。

### 3.2 最小可编译单元（MCCU）

```xiyi
struct Point {
    x: f32,
    y: f32,
}

#[effect(none)]
implement Point {
    pub fn new(x: f32, y: f32) -> Self {
        Self { x, y }
    }
    pub fn distance(&self, other: &Point) -> f32 {
        let dx = self.x - other.x;
        let dy = self.y - other.y;
        (dx * dx + dy * dy).sqrt()
    }
}

fn main() {
    let a = Point::new(0.0, 0.0);
    let b = Point::new(3.0, 4.0);
    let d = a.distance(&b);
}
```

这个示例覆盖了自举期的核心能力：
- 结构体定义
- 方法实现（`implement` 块）
- 所有权与借用（`&self`, `&Point`）
- 效果标注（`#[effect(none)]`）
- 基础运算与标准库调用（`.sqrt()`）

### 3.4 自举期"有语法但无运行时"的特性

| `checkpoint` 块 | 语法解析 | 需要图调度器 |

## 第四章 编译器开发路线推演

### 4.1 阶段划分原则

自举期编译器开发遵循"**前端先行、静态语义完整、后端渐进、图域占位**"的原则。

### 4.2 阶段一：最小可编译单元（MCCU）

**目标**：让那个 `Point::distance` 示例能够编译并运行。

**任务分解**：
1. **词法分析器（Lexer）**
   - 识别希夷的关键字（`let`, `var`, `fn`, `struct`, `implement`, `interface`, `model`, `actor`, `if`, `lack`, `while`, `for`, `loop`, `return`, `yield`, `gen`, `persist`, `deterministic`, `probabilistic`, `checkpoint`, `async`, `await`, `try`, `never`, `is`, `proto`）
   - 识别类型关键字（`i8`~`i128`, `u8`~`u128`, `f16`/`f32`/`f64`, `bool`, `char`, `str`, `Tensor`, `Sym`, `Dyn`, `Option`, `Result`, `Generator`, `DiffHandle`, `Gradient`, `GradMap`）
   - 处理属性语法（`#[...]`）
   - 处理泛型语法（`<...>`）
   - 处理管道操作符（`|>`）

2. **语法分析器（Parser）**
   - 实现递归下降解析器
   - 构建 AST（抽象语法树）
   - 支持表达式优先级（管道操作符优先级低于 `.`，高于赋值）
   - 支持 `model` / `actor` 块的降维（Desugaring）——在语法分析阶段或宏展开阶段完成

3. **基础语义分析**
   - 符号表构建
   - 类型检查（基础类型、复合类型、函数签名匹配）
   - 简单的借用检查（至少覆盖同一作用域内的 Move/Borrow 冲突）

4. **代码生成（LLVM IR）**
   - 对接 LLVM 后端
   - 生成可执行的机器码
   - 基础运行时（栈分配、函数调用）

**验收标准**：
```bash
$ xiyic src/main.xiyi -o main
$ ./main
# Point::distance 示例正确输出 5.0
```

### 4.3 阶段二：所有权系统完整实现

**目标**：实现 Rust 级别的所有权、借用、生命周期检查。

**任务分解**：
1. **借用检查器（Borrow Checker）**
   - 实现非词法生命周期（NLL）或等效算法
   - 处理 `&mut T` 与 `&T` 的互斥性
   - 处理跨函数的借用生命周期
   - 处理 `persist var` 的特殊冻结边界

2. **Move 语义**
   - 确定哪些类型实现 `Copy`（基础标量类型）
   - 非 `Copy` 类型的 Move 语义
   - `Drop`  trait 的自动推导与调用插入

3. **效果推导系统**
   - 从函数体推导 effect 集合
   - 验证用户标注与推导结果的一致性
   - `deterministic { }` 块的静态验证（Level 1：禁止显式 panic）

**风险点**：
- 借用检查器是 Rust 编译器中最复杂的模块之一，希夷需要复现其核心逻辑
- `persist` 的冻结边界是一种新的借用模式，没有现成参考实现

### 4.4 阶段三：张量类型与形状推断

**目标**：`Tensor<T, Shape>` 的完整类型检查与编译期形状推断。

**任务分解**：
1. **形状类型系统**
   - 将形状 `[3, 224, 224]` 表示为编译期常量类型
   - 实现 `Sym<N>` 的符号变量表示
   - 实现 `Dyn` 标记
   - 形状代数化简（常量折叠、线性项合并）

2. **张量算子的形状规则**
   - `linear`：输入 `[B, M]`，权重 `[M, N]` → 输出 `[B, N]`
   - `reshape`：验证元素总数守恒
   - `flash_attention`：验证注意力形状约束
   - 编译期非线性约束检测（`Sym<M> * Sym<N>` → 报错 `error[JIT001]`）

3. **隐私标签类型检查**
   - 实现隐私格 `(P, ⊑, ∨, ∧)` 的类型层面运算
   - `Rational128` 的编译期运算（零舍入误差）
   - `dp(0)` 自动推导禁令

**验收标准**：
```xiyi
let x: Tensor<f32, [3, 224, 224]> = load_image();
let y: Tensor<f32, [Sym<B>, 3, 224, 224]> = load_batch();
let z = x.linear(y, 256);  // ❌ 编译错误：形状不匹配
```

### 4.5 阶段四：图域静态语义完整实现

**目标**：所有图域代码可以通过编译，生成桩代码。

**任务分解**：
1. **`model` 块降维**
   - 语法分析阶段将 `model MLP { ... }` 转换为 `struct MLP { ... }` + `implement MLP { ... }`
   - 语义分析阶段注入 `Kind = Model`
   - 识别 `forward` 为保留名，自动注入 `#[effect(graph)]`
   - `Kind == Model` 的 struct 中，所有 `Tensor` 字段自动获得 `persist` 语义

2. **`DiffHandle<T>` 实现**
   - 定义为不透明类型（编译器内建）
   - 实现 `#[must_consume]` 属性（strict 模式编译错误，dev 模式警告）
   - 实现 `ExecutorLocal`（禁止 `Send`/`Sync`）
   - 方法体生成 panic 桩代码

3. **图域控制流检查**
   - 静态控制流：编译期常量条件 → 允许
   - 参数化控制流：`Sym<N>` 条件 → 允许，验证两分支形状兼容
   - 动态控制流：运行时张量值条件 → 编译错误（必须使用 `tensor.cond` / `tensor.while_loop`）
   - 禁止副作用、递归、运行时 `while`/`for`

4. **敏感度类型推导**
   - 编译期常数敏感度（`#[sensitivity(const = C)]`）
   - 函数复合规则：`C(f ∘ g) = C(f) × C(g)`
   - 分支规则：`C(if b then f else g) = max(C(f), C(g))`

**验收标准**：
```xiyi
model MLP {
    var layer1: Tensor<f32, [784, 256]>;
    fn forward(&self, x: Tensor<f32, [Sym<B>, 784]>) -> Tensor<f32, [Sym<B>, 10]> {
        x.linear(self.layer1, 256).relu()
    }
}
// 自举期：编译通过，运行时 forward 返回默认值或 panic
```

### 4.6 阶段五：控制流扩展与语法糖

**目标**：实现 Zeta 修正案中的全部控制流扩展。

**任务分解**：
1. **`lack if` / `lack if else`**
2. **`if bind` / `lack if bind`**
3. **`while bind`**
4. **`is` 模式测试**
5. **`gen fn` / `yield`** —— 生成器状态机转换
6. **`|>` 管道操作符** —— 语法糖，降维为嵌套函数调用
7. **`#[unroll(N)]`** —— 编译期循环展开
8. **`try` 块**
9. **`never` 类型**

**依赖关系**：
- `try` 块依赖 `Result<T, E>` 的完整实现
- `gen fn` 依赖状态机转换（类似 Rust 的 generator transform）
- `|>` 依赖函数类型的一等公民支持（或至少函数引用）

### 4.7 阶段六：Actor 与并发静态语义

**目标**：Actor 模型代码可以编译，消息协议静态检查通过。

**任务分解**：
1. **`actor` 块降维**
   - 转换为 `struct` + `implement`
   - 注入 `Kind = Actor`
   - 识别 `receive` 为保留名

2. **`proto` 定义与验证**
   - 消息变体类型检查
   - 发送端检查：消息变体必须属于目标 Actor 的 `proto`
   - 接收端穷尽性检查：`match` 必须覆盖所有变体

3. **`!` 消息发送**
   - 语法解析
   - 所有权转移检查
   - 返回类型 `Result<(), SendError<T>>`

4. **`async` 块基础**
   - 语法解析
   - 分层快照策略（简化版：所有非 Copy 字段必须显式 `snapshot`）
   - 状态机转换（类似 Rust 的 async transform）

**注意**：自举期 Actor 运行时不在编译器内，编译器只负责静态检查。

### 4.8 阶段七：标准库 L0 + L1 实现

**目标**：实现 `xiyi-core`（`no_std` 兼容）。

**任务分解**：
1. **L0 语言内建**
   - 基础类型的内建方法（`abs()`, `checked_add()`, `overflowing_mul()` 等）
   - 关联常量（`MIN`, `MAX`, `NAN`, `INFINITY` 等）
   - 张量类型的内建算子命名空间

2. **L1 `xiyi-core`**
   - `Copy`, `Clone`, `Send`, `Sync`, `ExecutorLocal`, `Idempotent`, `Label`, `KernelSigned` 接口
   - `Rational128` 完整实现（128位精确有理数运算）
   - 切片操作、裸指针封装
   - 确定性算法

3. **L2 `xiyi-std`（部分）**
   - `Vec<T>`, `String`, `HashMap<K, V>`
   - `Option<T>`, `Result<T, E>` 的完整方法集
   - 基础 IO（`open`, `read_file` 等）

**约束**：
- 标准库不引入隐式全局状态
- `TrainingContext`、随机数生成器、设备句柄等均须显式创建并传递

## 第五章 风险推演

### 5.1 技术风险

| 风险项 | 等级 | 描述 | 缓解措施 |
|--------|------|------|---------|
| 借用检查器复杂度 | **高** | Rust 的借用检查器开发耗时数年，希夷需要复现、扩展（`persist` 冻结边界） | 复用 Rust 的 Polonius 算法或类似框架；`persist` 作为特殊 case 处理 |
| 张量形状推断完备性 | **高** | 编译期形状推断需要处理符号代数，非线性约束检测容易误报/漏报 | 限制编译期仅做局部代数化简；非线性约束明确报错，不进入 JIT |
| 图域降维的正确性 | **中** | `model` 块降维为 struct + implement 后，必须保留全部语义（Kind 标记、自动 persist、forward 识别） | 大量测试用例覆盖；形式化验证降维前后的语义等价性 |
| 生成器状态机转换 | **中** | `gen fn` / `yield` 需要状态机转换，与借用检查器交互复杂 | 参考 Rust 的 generator 实现；自举期可延后实现 |
| 隐私标签的性能 | **中** | `Rational128` 的编译期运算可能影响编译速度 | 编译期仅存储类型信息，不执行复杂运算；必要时缓存 |

### 5.2 依赖风险

| 依赖项 | 状态 | 风险 |
|--------|------|------|
| WujiOS 内核 | 开发中 | 自举期编译器运行在 WujiOS 上，需要稳定的系统调用接口 |
| WujiOS AI 子系统 | 未就绪 | 图域实际运行依赖此子系统，自举期只能做静态检查 |
| NPU 驱动 | 未就绪 | 图域内存管理（256字节对齐、HBM分配）需要硬件支持 |
| LLVM 后端 | 可用 | 代码生成依赖 LLVM，风险较低 |

**推演**：如果 WujiOS AI 子系统延迟交付，自举期编译器仍然可以完成全部静态语义实现，但图域代码只能运行桩代码。这不会影响自举编译器自身的开发，但会延迟希夷作为"AI 原生语言"的实际可用性。

### 5.3 资源与进度风险

| 风险项 | 等级 | 描述 |
|--------|------|------|
| 规范迭代超支 | **中** | 当前 `_Kappa` 剩余 9 次希腊字母迭代，如果自举期超过 9 次规范修订，需要进位到 `v0.1.9.7` | 
| 范围蔓延 | **高** | 开发者容易将"自举期"与"完整语言"混淆，试图在自举期实现全部特性 | 严格对照《最小子集概要》，任何超出范围的需求必须明确拒绝或标记为"后自举期" |
| 测试覆盖不足 | **中** | 类型系统复杂度高，边界情况多 | 建立"反例征集"机制（文档 §13.1），鼓励社区提交反例 |

## 第七章 关键决策推演

### 7.1 决策一：是否自举期就实现完整的 NLL（非词法生命周期）？

**选项 A**：完整 NLL（Rust 2018+ 级别）
- 优点：借用检查更精确，开发者体验好
- 缺点：实现复杂度高，可能延迟自举期 2-3 个月

**选项 B**：简化版生命周期（词法作用域为主）
- 优点：实现快，风险低
- 缺点：某些合法代码会被拒绝，开发者体验稍差

**推演建议**：选择 **选项 B（简化版）**，但在架构上预留 NLL 的扩展接口。自举期的目标是"能编译自己"，不是"完美"。Rust 本身也经历了从词法生命周期到 NLL 的演进。

### 7.2 决策二：`model` 块降维发生在哪个阶段？

**选项 A**：语法分析阶段（Parser 中直接降维）
- 优点：后续阶段看不到 `model`，实现简单
- 缺点：错误信息会指向降维后的代码，用户困惑

**选项 B**：语义分析阶段（保留 `model` AST 节点，类型检查后再降维）
- 优点：错误信息可以保留 `model` 上下文
- 缺点：语义分析器需要特殊处理 `model` 节点

**推演建议**：选择 **选项 B**。`model` 块是希夷的核心概念，错误信息必须对用户友好。可以在语义分析阶段保留 `model` 的 Kind 信息，代码生成阶段再降维。

### 7.3 决策三：隐私标签的编译期运算粒度

**选项 A**：完整 Rational128 运算（零舍入误差）
- 优点：精确，符合规范
- 缺点：编译期运算开销大

**选项 B**：浮点近似（编译期用 f64，运行期用 Rational128）
- 优点：编译快
- 缺点：可能引入舍入误差，导致类型系统不一致

**推演建议**：选择 **选项 A**，但引入缓存机制。隐私标签的运算只在类型检查阶段执行，且结果可以缓存。`dp(0)` 禁令和 `δ = 1/1000000` 的粒度限制减少了实际运算复杂度。

### 7.4 决策四：自举期是否支持 `async`/`await` 的完整状态机？

**选项 A**：完整支持（类似 Rust 的 async transform）
- 优点：功能完整
- 缺点：实现复杂，需要 Pin、Future trait 等基础设施

**选项 B**：语法解析 + 简单状态机（仅支持基础场景）
- 优点：实现快，覆盖大部分用例
- 缺点：复杂场景（自引用结构）不支持

**推演建议**：选择 **选项 B**。自举期的 `async` 主要用于 Actor 消息处理，场景相对简单。完整支持可以放在后自举期。

## 第八章 与 WujiOS 的协同推演

### 8.1 接口契约

自举期编译器与 WujiOS 的交互点：

| 交互点 | 自举期状态 | WujiOS 提供 | 编译器假设 |
|--------|-----------|-------------|-----------|
| 系统调用 | 需要 | 稳定的 syscall 接口 | `#[system_api]` 属性标记的函数 |
| 内存分配 | 需要 | `malloc`/`free` 或等价接口 | 栈域堆分配 |
| 文件 IO | 需要 | `open`/`read`/`write` | `#[effect(io)]` 函数 |
| AI 子系统 | 不需要 | 未就绪 | 图域生成桩代码 |
| NPU 驱动 | 不需要 | 未就绪 | 图域不生成设备代码 |
| Actor 运行时 | 不需要 | 未就绪 | Actor 生成桩代码 |

### 8.2 图域的"零改动生效"承诺

文档 §5 明确指出："待 AI 子系统就绪后零改动生效"。

**推演**：这要求编译器前端必须将图域的语义完全编码在 IR（中间表示）中，后端可以根据目标平台选择：
- 自举期：生成桩代码（CPU 上运行空函数）
- AI 子系统就绪后：生成真正的图调度器调用 + NPU 设备代码

这意味着 IR 设计必须预留图域的完整语义信息，不能在前端就丢失。

## 第九章 结论：自举期的真正目标

### 9.1 一句话总结

**自举期的真正目标不是"让希夷能写 AI 程序"，而是"让希夷能编译自己，同时保留全部 AI 语义的静态检查能力"。**

### 9.2 三层能力模型

| 层级 | 自举期目标 | 后自举期目标 |
|------|-----------|-------------|
| **语法层** | 完整解析所有语法（包括 AI 语法） | 保持不变 |
| **静态语义层** | 完整类型检查、所有权检查、效果检查、形状推断 | 保持不变 |
| **动态语义层** | 栈域完整执行；图域/Actor/AI 语法生成桩代码 | 图域实际执行，AI 子系统联调 |

### 9.3 对开发者的意义

开发者在自举期可以：
1. ✅ 用希夷编写系统程序（栈域完整支持）
2. ✅ 用希夷编写 AI 模型代码并做编译期类型检查（图域静态语义）
3. ✅ 用希夷编写 Actor 并发程序并做协议检查（Actor 静态语义）
4. ❌ 在自举期实际运行 AI 训练、推理（需要 WujiOS AI 子系统）
5. ❌ 在自举期实际运行 Actor 消息传递（需要 WujiOS Actor 运行时）

### 9.4 下一步行动

1. **冻结《最小子集概要》v0.1.9.6_Delta**：明确划定自举期工作边界，防止范围蔓延
2. **搭建 CI/CD**：为每个里程碑建立自动化测试，特别是"反例征集"的回归测试
3. **编写教学文档**：将"栈域/图域"作为第一章教学，避免开发者困惑
4. **与 WujiOS 团队对齐**：明确 AI 子系统的接口契约和时间表
5. **启动编译器前端开发**：Lexer → Parser → 基础语义分析 → 借用检查器
